# v0.6.0 — advisory locking on `std::fs::File`; MSRV 1.89

v0.6.0 is a minor release. Advisory file locking moves from the small in-repo
`libc::flock(2)` wrapper (introduced in v0.5.2) to `std::fs::File`'s inherent
`lock`/`unlock`, which stabilized in Rust 1.89.0. The minimum supported Rust
version rises from 1.82 to 1.89 in the same change.

## What changed

- The in-repo `src/file_lock.rs` module is deleted. All eleven exclusive-lock
  sites now call `std::fs::File::lock`; telemetry's eager explicit unlocks call
  `File::unlock`; the recovery, history, and first-run paths keep their
  drop-on-close discipline. `std::fs::File::lock` is blocking-exclusive
  (`flock(2)` `LOCK_EX`, no `LOCK_NB`), `unlock` releases, and dropping a
  locked file releases — identical behavior to the in-repo wrapper and to
  `fs2` before it.
- MSRV is now 1.89.0. The `libc` dependency stays; several modules still use
  `libc::poll`/`pipe`/signal helpers directly.
- A `cargo-deny` configuration and a separate, decoupled supply-chain workflow
  (`cargo deny check` over advisories, licenses, bans, and sources) are added.
  The workflow is intentionally non-gating and not wired into the release gate,
  so an advisory-db state change can never block a release.
- Committed Python bytecode caches are untracked and `__pycache__/` is now in
  `.gitignore`.

## Not a behavior change for callers

The locking migration invokes the same advisory-lock semantics over the same
syscall family. There is no new external dependency from the locking change.
Existing scripts, configuration, and wire contracts are unaffected; only the
toolchain requirement moved.

## Verification

The full Rust suite (324 library, integration, and corpus tests, including the
relocated blocking-exclusive lock contract), `cargo clippy -D warnings`,
`cargo fmt --check`, the `cargo +1.89.0 check` MSRV gate, `cargo deny check`,
`scripts/check-docs.py`, and `scripts/provider-bakeoff.py --self-test`.
