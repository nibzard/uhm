# uhm v0.3.0 — tmp-drive evaluation report

> Generated by an automated 38-task battery (36 core + 2 pty) run against the
> checksum-verified v0.3.0 release binary, in a disposable `/dev/shm` tmpfs sandbox
> with an isolated HOME/XDG env, `UHM_TELEMETRY=off`, `--plain --json --fresh`,
> provider = OpenAI (default). Deterministic fixture corpus with known exact counts/sums.

## Headline

- **First-pass (mechanical): 29/38 tasks PASS.**
- **After contract-aware analysis: 37/38 original scenarios conformed; one exposed an `ask` routing-reliability issue.**
- 8/8 corrected round-2 invocations passed. Seven added the documented `--force` authorization; B9b changed `ask` to `auto`, so it demonstrated a workaround rather than validating the original `ask` scenario.
- End-to-end latency: p50 **2531 ms**, p95 **6228 ms** (n=33, non-introspection tasks; one attempt reached 10651 ms).
- Generated Python programs produced **numerically exact** results vs the known corpus (CSV sum, group-by sums, status-code histogram, key set).

## Setup

- Install: official installer (`curl ... install.sh | sh`) replaced stale local `0.1.0`; `uhm --version` = 0.3.0; SHA256 verified by installer; `uhm doctor` and `uhm doctor network` exit 0 (OpenAI auth OK, Python 3.12.3 isolated runtime OK).
- Sandbox: `/dev/shm/uhm-eval` (5.9 GB RAM tmpfs); corpus in `work/` (NOTES.md 5 paragraphs/95 words, events.log 60 lines with known status histogram, sales.csv 40 rows / amount sum 82195, data.json, rust+py source with TODOs, sized files, git repo).
- Model configuration: OpenAI `gpt-5.6-terra` (then-default), reasoning effort `low`, streaming enabled, context `standard`; the client supplied no temperature parameter.
- Each NL task invoked as `uhm [--plain --json --fresh] [mode] <intent>`; result on stdout, `uhm`/`uhm.child` envelope on stderr; exit code + filesystem state asserted per task.
- Each model-routed scenario ran once. Results therefore establish observed behavior, not a statistical reliability rate.

## Findings & behavioral notes

1. **Non-interactive mutations require `--force`.** In piped/non-TTY mode, `run` executes read-only and benign-create actions (`touch newfile`, `mkdir`) but pauses *any* mutating action — rename (`mv`), redirect-writes (`date > now.txt`), and generated-program writes — returning rc=11 with message *"review is required; automation must use --force or --dry-run."* This is deliberate: scripted use must opt into mutation. Round 2 confirmed all such tasks succeed with `--force`.
2. **Piped `ask` exposed a routing-reliability issue.** `uhm ask summarize…` is a valid prose request, but the model proposed local execution and the client returned rc=10 `route_contract_error`. Refusing the executable proposal was correct; failing to obtain an answer was not the desired UX. B9b showed that `auto` could complete the work, but changing routes did not validate the original scenario. A subsequent source change restricts `ask`/`explain` to answer and clarification tools at the provider boundary; that change requires a fresh evaluation and is not part of this v0.3.0 result.
3. **Ambiguous intents return clarification (rc=12).** Vague *"remove old build artifacts"* and *"fix the data"* both returned `clarification_required` (rc=12) with a concrete follow-up question, rather than guessing destructively. No corpus file was modified.
4. **Parent-shell actions are typed, not applied.** `uhm run cd ..` in non-TTY returned rc=11 `requires_parent_shell` (the base binary cannot mutate its parent shell) — exactly per the documented contract.
5. **Dry-run is byte-exact and side-effect-free.** `--dry-run` printed the exact proposal (`: > marker.tmp`, `mv -- marker.tmp marker.done`, a full generated Python program) and touched nothing (verified by post-run file existence).
6. **Missing-input degrades cleanly.** *"paragraphs in missingfile.md"* returned rc=1 with a message (no panic/crash).
7. **Hyphen-leading intents.** `uhm -- -list the files` was accepted as intent (rc=0), not misparsed as flags (not rc=2).
8. **Interactive paths under a pty.** Bonus pty tasks (via `script`) worked: default TTY path answered `60`, and `--review` + cancel returned rc=11 with nothing written.
9. **History corroborates.** `uhm history status` recorded 45 runs / 292 metadata events; `history list` shows both `run_shell` and `run_program` routes and a flagged failed child — consistent with the captured envelopes.

## Limitations

- These are 38 scenarios, not an exhaustive enumeration of product capabilities.
- Model-routed tasks were single attempts, so the run does not measure stochastic consistency.
- Timing is end-to-end wall time and does not isolate provider latency.
- The battery covered exact values and filesystem effects well, but assessed open-ended prose quality only superficially.
- This live battery did not directly exercise every adversarial boundary covered elsewhere in the repository, including symlinks, path traversal, malformed structured data, resource exhaustion, interrupted processes, and hostile embedded instructions.

## Conclusion

The first-pass mechanical rate was 29/38. Contract-aware review found that eight apparent failures came from incorrect harness expectations around non-TTY mutation authorization or ambiguity; corrected invocations passed. The remaining B9 result was safe but revealed an `ask` routing-reliability issue. Thus **37/38 original scenarios conformed to the intended behavior**, while generated-program outputs were numerically exact and the observed safety controls behaved as documented. This is strong release-candidate conformance evidence, not proof that the full advertised surface is defect-free.
