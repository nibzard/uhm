# Plan 10 — Harden v0.2 and ship v0.2.2

## Purpose and dependency

This plan repairs the trust-boundary, crash-consistency, execution-bound, history, CLI, installation, and release-assurance defects found in the post-release review of `v0.1.0..v0.2.1`. It depends on the capabilities delivered by Plans 4–7. It does not add another execution runtime or broaden `uhm`'s authority.

The published v0.2.1 release is immutable and remains available as historical evidence. These fixes land on `main`, preserve the already-written `history replay` notice-gating regression fix, bump the patch version, and ship as v0.2.2. Plan 9's provider benchmark is independent and must not become a prerequisite for this corrective release.

The release goal is not merely a green current test suite. The goal is to make the following statements mechanically true under failure, concurrency, proxy, and hostile-child-process tests:

1. `--local-input` bytes, including copies embedded in child-derived output, cannot enter any OpenAI request.
2. No telemetry POST starts without current notice and opt-out authorization, and `telemetry off` returns only after local send activity is quiescent.
3. Program wall time includes primary-process waiting, descendant-held pipe drainage, and bounded cleanup.
4. Managed commit and restore state can be reconciled after every durable rename boundary without inventing verified recovery.
5. Dry-run commands do not mutate state, configured retention bounds are real, and history deletion cannot silently delete separately consented recovery evidence.
6. History, context previews, telemetry, help, documentation, and release artifacts describe the behavior that actually occurred.

## Release posture and priorities

Every confirmed finding in this plan must close before v0.2.2. The P0/P1 workstreams block code freeze; the P2 installation, packaging, documentation, and workflow items block publication. Do not publish a partial privacy/recovery patch and defer its release-assurance fixes.

| Priority | Workstream | Why it comes here |
| --- | --- | --- |
| P0 | Outbound authorization and local-input privacy | Prevents content or telemetry from leaving contrary to explicit user controls |
| P0 | Program deadline and recovery crash safety | Prevents unbounded hangs and false or unrecoverable recovery outcomes |
| P1 | Recovery lifecycle, history integrity, and CLI truthfulness | Makes advertised local evidence, dry-run, and review semantics dependable |
| P1 | Telemetry semantics and proxy coverage | Restores the bounded measurement path without weakening consent |
| P2 | Installation, documentation, packaging, and release gating | Makes the next release installable and prevents publication ahead of its quality gate |

Tracks may be implemented in parallel, but their merge order is constrained:

```text
outbound send gate ──→ telemetry enum/proxy fixes ──┐
                                                   ├─→ full quality gate ─→ v0.2.2
program deadline ────→ program traversal tests ────┤
recovery reconcile ──→ retention/history deletion ┤
CLI operand model ───→ context/docs/install ───────┘
```

## 0. Preserve the v0.2.1 fixes and carry-in regression

Before restructuring these paths, pin the behavior already corrected in v0.2.1 and the current uncommitted replay fix. Keep end-to-end contract coverage for:

- environment proxy discovery on the OpenAI, doctor, and telemetry HTTP agents;
- `doctor` returning 13 when any selected health check fails;
- invalid `--shell` and `--context` values returning 2 during argument parsing;
- purely local commands skipping the first-use notice and marker;
- `history replay` taking the outbound notice gate before any completion telemetry;
- current version text in CLI, doctor hints, privacy examples, release documentation, and archives; and
- pinned recovery entries surviving ordinary pruning until explicitly unpinned.

These tests are the baseline for refactoring, not substitutes for the adversarial cases below. Carry the existing `src/args.rs` and `tests/cli_contract.rs` replay patch into the first implementation branch without mixing in unrelated Plan 9 files.

## 1. Put every outbound path behind one authorization boundary

### 1.1 Centralize telemetry sending and make opt-out quiescent

Replace the separate send behavior in interaction completion, explicit feedback, and parent-shell acknowledgement with one internal send gate.

The gate must:

1. Acquire `send.lock` before any queue claim, event update, or POST.
2. Re-read the persistent disabled marker and current environment/config policy while holding the lock.
3. Verify that the current notice revision marker exists before starting a POST.
4. If notice is absent, retain or update the queued event without sending it.
5. Use one lock order everywhere: `send.lock` before `queue.lock`. No path may acquire these in reverse order.
6. Hold `send.lock` until the POST attempt has reached a terminal local state.

`telemetry off` continues to write the disabled marker first, then takes `send.lock`, clears queued and claimed files under `queue.lock`, and returns only after prior send holders have completed. A sender that acquires the lock afterward must observe the disabled marker and stop.

Inject the HTTP transport behind a narrow test interface so concurrency tests can pause immediately before POST without using the public network. Add deterministic tests for:

- missing notice marker during `shell-ack`;
- an opt-out marker appearing before the send lock is acquired;
- `telemetry off` racing with acknowledgement before queue update, after claim, and immediately before POST;
- feedback and ordinary completion following the same gate;
- queue recovery when notice is absent; and
- the absence of deadlock under repeated concurrent acknowledgement, completion, and opt-out.

Acceptance criteria:

- No POST begins unless both notice and telemetry policy are valid under `send.lock`.
- Once `telemetry off` returns, no local telemetry send is running or can begin until a later explicit enablement.
- Parent acknowledgement still updates a queued parent outcome without exposing a run identifier in the payload.

### 1.2 Prevent local-input-derived content from entering repair

Treat child stdout and stderr as content-bearing and potentially derived from every file the program can read. Sanitizing terminal control sequences does not make that content safe to send.

For a program executed with `--local-input`:

- keep the diagnostic tail available locally in the terminal and optional local history according to history settings;
- exclude stdout, stderr, exception text, paths printed by the child, and all other child-derived strings from a model repair follow-up;
- send only allowlisted non-content fields such as exit category, numeric status, signal category, timeout/overflow flags, and harness-generated failure class; and
- preserve the prior typed program source because it already came from the provider, while ensuring no local input was interpolated into it.

Represent diagnostic provenance explicitly rather than relying on call-site discipline. A repair payload builder should accept typed coarse outcomes and should require a separate content-bearing value only on the ordinary, non-local-input path.

Add a request-capture regression in which generated Python reads `UHM_PROGRAM_LOCAL_INPUT`, writes a unique sentinel to stderr, and fails. Exercise repair and inspect every serialized request. Repeat for stdout, an exception containing the sentinel, and a path derived from local bytes.

Acceptance criteria:

- The sentinel appears in neither the initial request nor any repair request.
- Ordinary non-local-input repair can still include the bounded diagnostic tail after the existing local preview.
- Tests inspect serialized request bodies, not just UI output.

### 1.3 Make retained-history repair an explicit disclosure

`uhm repair` is a second content-bearing history operation and must not be hidden behind privacy text that names only recovery.

Before a repair request:

1. Build one bounded structured subset containing only retained intent, typed proposal, coarse outcome, and optional feedback.
2. Render the exact subset and the fixed instruction that will be sent.
3. State that current context is added under the normal context policy.
4. Require affirmative TTY approval; EOF, rejection, and non-interactive invocation send nothing.
5. Use the exact approved bytes as the request seed so preview and payload cannot diverge.

Share the preview-and-approval helper with best-effort recovery while keeping their labels and instructions distinct. Update `PRIVACY.md`, the privacy guide, local-history guide, and CLI reference to name both explicit receipt exceptions.

Add approval, rejection, EOF, non-TTY, and preview-equals-payload tests with unique sentinels in each field.

## 2. Make the program harness bounded through cleanup

### 2.1 Extend the wall deadline through pipe drainage and descendant cleanup

The wall deadline must govern the entire harness-owned lifecycle, not only `Child::try_wait` for the primary Python process.

Refactor pipe collection so reader work can stop at a shared deadline even when a detached or background descendant still holds a writer descriptor. On supported Unix hosts, use nonblocking reads or polling with a cancellation/deadline signal; do not rely on an unbounded `JoinHandle::join` after the primary exits.

Keep the process-group identifier installed until:

- the primary child is reaped;
- both output collectors have reached EOF or the shared deadline;
- lingering group members have received TERM, then KILL after the bounded grace period; and
- the collectors have exited.

If the primary exits but inherited pipes remain open through the deadline, classify the result as a timeout and return status 124. Best-effort group termination remains honest about descendants that deliberately create a new session, but those descendants must not keep the uhm process blocked.

Add tests for:

- a primary process that sleeps past the deadline;
- a primary process that exits zero after spawning a child that inherits both pipes;
- a child that ignores TERM;
- a descendant that creates a new session while retaining a pipe;
- output overflow combined with a lingering child; and
- Ctrl-C while descendants are present.

All tests must assert elapsed time is below the configured timeout plus a small platform-specific cleanup allowance and must verify no in-group child remains. A new-session fixture must report its PID and either self-expire promptly or be explicitly terminated by test cleanup; the suite must prove it leaves no background process behind even though production process-group cleanup cannot reach it.

### 2.2 Measure only the private workspace tree

Replace `metadata()` traversal with `symlink_metadata()` and never descend through symlinks. Reject symlink entries in a successful workspace, or count their link object without following it; choose one behavior and document it. Stop traversal as soon as the configured limit is exceeded rather than scanning the rest of the tree.

Add tests for links to `/`, a self-referential link, a link to a large external tree, nested regular directories, and an early over-limit result. The harness must return promptly and must never enumerate outside the temporary workspace.

## 3. Make recovery state durable, monotonic, and bounded

### 3.1 Reconcile every managed-commit crash boundary

Persist enough intent before rename to distinguish these resume cases for both replacements and new files:

| Staging | Destination | Persisted item state | Resume action |
| --- | --- | --- | --- |
| Expected staged hash exists | Original preimage/absence matches | staged/rename-pending | Perform the rename and verify |
| Missing | Matches staged hash and mode | staged/rename-pending | Reconcile as committed, fsync, and persist `Committed` |
| Missing or changed | Does not match staged or original evidence | any incomplete state | Fail closed as conflicted/corrupt |
| Irrelevant | Matches persisted postimage | committed | Verify and continue idempotently |

Either add an explicit per-item `RenamePending` state or document `Staged` as the durable rename intent. The required ordering is:

1. hash and fsync staging;
2. persist staged hash, mode, and rename intent;
3. rename;
4. fsync the destination directory;
5. reopen and verify the destination;
6. persist postimage evidence and `Committed`.

Add test-only fault injection immediately before rename, immediately after rename, after directory fsync, after destination verification, and before/after manifest persistence. Cover existing files, new files, and each item position in a multi-output commit.

Acceptance criteria:

- Resume is idempotent from every injected boundary.
- A destination already matching the staged evidence is never overwritten again.
- Unrelated destination changes are never accepted as a completed commit.

### 3.2 Make forced provenance sticky

Once any restore invocation begins with force, set `manifest.forced_restore = true` and derive every later check, reason, history event, and operation outcome from:

```text
effective_forced = manifest.forced_restore || current_invocation_forced
```

No resume path may downgrade that value. Add a multi-item test that interrupts after the first forced item, resumes through ordinary `undo`, and asserts that the final manifest and report remain `forced_restore`. Repeat from both `undo_preflight` and `undo_in_progress`.

### 3.3 Make dry-run byte-for-byte read-only

Separate prune planning from prune application. Planning returns an immutable list of manifest transitions and snapshot paths; application performs deletion and tombstone writes only when `dry_run == false`.

Tests must snapshot the complete recovery tree before and after dry-run for:

- replacement snapshots;
- new-file-only manifests with no snapshot file;
- pinned manifests;
- already restored manifests; and
- mixed over-age/over-byte candidates.

The before and after trees, including mtimes where practical, must be identical.

### 3.4 Enforce global retention and manage stale preparation

The configured total is global across retained recovery snapshots, not a per-run allowance.

Under the recovery lock, perform a bounded validated usage calculation before accepting new snapshot bytes. Prune eligible oldest/expired entries according to policy or refuse capture with an actionable diagnostic when pinned data, the scan bound, or active operations prevent proving sufficient capacity. A successful capture must never leave retained bytes over `max_total_bytes`.

Add an explicit preparation lease tied to the configured program deadline and cleanup allowance. A `preparing` manifest whose owner is still valid remains active. A manifest beyond its lease, with no transition to `commit_partial`, can be safely abandoned through validated cleanup because no managed rename has begun. Record the terminal state or tombstone rather than leaving an unmanageable directory.

Do not auto-delete `commit_partial`, `undo_preflight`, or `undo_in_progress`; those remain resumable or explicitly conflicted.

Test repeated captures across runs, age expiry, pinned over-cap data, scan-limit uncertainty, a crash during snapshot copy, a crash after preparation but before spawn, and concurrent capture/prune.

### 3.5 Separate history deletion from recovery deletion

`history clear --all` clears the journal and ordinary history artifacts while preserving any run directory containing a validated recovery manifest. Report how many recovery runs were preserved. Only `recovery prune` and `recovery off --prune` may delete separately consented snapshot evidence.

Reuse the validated descendant and symlink protections already used by pruning. Add an end-to-end test that records history and a recoverable replacement, clears all history, and then successfully previews and completes undo.

## 4. Make local history complete and redaction structural

### 4.1 Replace export denylisting with an allowlisted export schema

Default redacted export must construct an export-specific value from explicitly permitted categorical fields. It must not serialize a full event and then remove a growing list of keys.

Exclude run and relationship identifiers, intent/proposal/artifact hashes, recovery reasons, paths, source, output, diagnostics, and checksums derived from removed values. Either omit integrity data from redacted export with a documented export schema or compute a new `export_checksum` over the final redacted representation; never retain the original journal checksum after mutation.

Build table-driven fixtures for every `EventKind`, including recovery events, proposals, artifacts, output capture, feedback, and linked runs. Assert prohibited key names and sentinel values are absent. `--include-content` remains an explicit local disclosure and preserves the journal representation without snapshot files.

### 4.2 Enforce the full-history content bound

When full history retains an intent, cap the retained UTF-8 string at a valid character boundary, record original and retained byte counts, and set the truncation flag from the actual retained value. If exact intent is required for `repair` or `recover`, reject a truncated source with a precise unavailable result rather than silently sending an incomplete job.

Test ASCII, multibyte UTF-8 at the boundary, a one-byte configured cap, and input larger than the default cap.

### 4.3 Journal every execution attempt before offering repair

Separate local attempt recording from the final interaction summary. After each child exits, append an ordered attempt event—including coarse effects, result, signal/timeout, and locally permitted diagnostics—before displaying repair/edit choices. A repair then records a replacement event and a second execution attempt.

Do not send two interaction telemetry summaries. Feedback projection should select the final job outcome while the local timeline retains both attempts.

Test shell and program sequences for failure→model repair→success, failure→local edit→failure, and failure→stop. The timeline must show what executed and in what order, including side-effecting failures.

## 5. Restore telemetry semantics and proxy assurance

### 5.1 Separate UI labels from stable wire enums

Give `Effect` a stable wire projection such as `telemetry_value()` or use its existing snake-case serde representation. Keep `label()` exclusively for user-facing prose.

Use stable values in interaction summaries and new history receipts. When deriving feedback from v0.2.1 history, accept both legacy human labels and new stable identifiers so existing receipts do not collapse to `none`. Map `run_program` to `program` explicitly.

Add tests that:

- construct a summary for every `Effect` variant and pass `Event::validate`;
- cover shell, program, parent-shell, answer, and clarification routes;
- prove nonempty shell effects no longer drop completion events;
- project both legacy and current receipts; and
- send worker-schema fixtures for every allowed enum.

Keep best-effort production behavior, but make an invalid internally generated event fail loudly in tests so schema drift cannot become silent data loss again.

### 5.2 Centralize and test proxy-enabled HTTP construction

Use one helper for the OpenAI API, doctor network check, and telemetry HTTP agents. It must apply environment proxy discovery consistently while retaining each caller's timeout and response policy.

Separate proxy-policy tests from deadline tests. Deadline tests must be deterministic regardless of ambient `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, or `NO_PROXY`; serialize any process-environment mutation. Positive local-proxy tests must observe all three production agents connecting through the proxy, while negative tests cover unreachable proxies and bounded failure.

Run the complete Rust suite once normally and once with representative proxy variables set in CI.

## 6. Preserve CLI operands and re-evaluate the action actually run

### 6.1 Rebuild shell actions after an edit

An initial review edit must re-enter the same validation loop as a model replacement. After editing:

- validate the exact new command bytes;
- rerun parent-shell detection;
- rerun requirement and shell availability checks using metadata that applies to the edited command;
- recompute safety tier and detected effects;
- display a fresh preview and any consequential confirmation; and
- record the edited proposal/effects rather than the original metadata.

Mark the action as user-edited and avoid presenting stale model assumptions or requirements as facts. Keep the global replacement/execution budget unchanged.

Test edits from benign commands into a typed parent action, destructive command, unavailable executable, control/NUL-invalid input, and ordinary read-only command.

### 6.2 Preserve management-command argv boundaries

Keep the natural-language prompt string for model-bound jobs, but add an exact operand vector for management subcommands. Do not reconstruct paths, IDs, flags, feedback, or guidance with `split_whitespace()`.

Migrate history, recovery, repair, recover, feedback, context, doctor, telemetry, and internal integration parsing to the operand vector. Continue accepting the old explicit `--` separator, but make the documented forms work:

```text
uhm repair last retry with UTF-8
uhm recover last preserve the manual edits
uhm history export --output "/tmp/export file.jsonl"
```

Reject missing option values, unknown management flags, and extra fixed-arity operands at parse/management time with exit 2. Add contract tests for spaces, Unicode, leading hyphens, empty values, and backward-compatible separator forms.

### 6.3 Share exact context construction and skip outbound consent for local work

Extract one context-composition path that resolves CLI/config shell precedence, gathers the selected mode, and adds validated integration/session fields. Use it immediately before model requests and in `context show`.

Determine local-only behavior before asking permission to send an optional shell-history entry. Ordinary local commands ignore the captured entry and never prompt. `context show` may display a wrapper-supplied history candidate only in a separate local diagnostic field marked `pending_approval`; it must not include that value in the displayed outbound context. Model-bound jobs retain the explicit preview and approval before adding it to outbound context.

Tests must compare the base context from `uhm --json context show` with the captured base context of a no-send request harness under CLI/config shell overrides, active Bash/Zsh/Fish integration, and optional history enabled/disabled. Test outbound history equality separately after simulated approval. Local management commands with wrapper-supplied history must succeed non-interactively without prompting.

### 6.4 Make parent-shell fallback honest for every accepted shell

Implement valid fallback rendering for POSIX `sh`, `pwsh`, and `powershell`, including quoting and environment operations, or explicitly report that a typed fallback is unavailable. Never default an unknown family to Bash syntax.

Keep installed wrapper support limited to Bash, Zsh, and Fish unless a real wrapper is implemented. Messages for `sh` and PowerShell must not recommend unsupported `shell-init` values; they should explain how to apply the rendered command manually.

Parameterize renderer and CLI tests across `sh`, Bash, Zsh, Fish, `pwsh`, and `powershell`.

## 7. Make distribution and documentation executable contracts

### 7.1 State the real child-environment boundary

For ordinary shell execution, retain the current compatibility policy: remove `OPENAI_API_KEY`, private/control-prefixed uhm variables, and user-configured `execution.deny_env` names. Do not claim that arbitrary AWS, GitHub, database, or agent credentials are removed when the child intentionally inherits the user's shell environment.

Generated Python remains different: it starts from an empty environment and receives only the documented allowlist. Keep those two policies visibly separate in configuration, behavior, privacy, and security documentation. Add tests for the exact shell deny behavior and the program allowlist.

A broader shell environment allowlist would change command compatibility and belongs in a separately reviewed product change, not an undocumented patch.

### 7.2 Repair and test installation instructions

Update the binary-install flow to:

- create `${HOME}/.local/bin` before installation;
- extract and install from the exact selected archive directory rather than a wildcard;
- filter `SHA256SUMS` to the selected archive for both GNU `sha256sum` and macOS `shasum`;
- provide valid separate Bash/Zsh and Fish PATH commands; and
- retain the Gatekeeper warning without encouraging checksum bypass.

Make the checked-in installation code blocks consume a shared tested script, or extract and execute those exact blocks in CI. Run them against a synthetic release archive and manifest in an empty temporary home: the Linux form on Linux and the macOS checksum/PATH form on macOS. A separate installer test that can drift from the published commands is insufficient.

### 7.3 Eliminate user-facing reference drift

Define one canonical documented basename set (`auto`, `sh`, `bash`, `zsh`, `fish`, `pwsh`, and `powershell`) and derive help/example text from it where possible. Add a contract test ensuring built-in help, `config.example.yaml`, and the parser agree on that set. Test accepted full executable paths and the internal empty auto-detect value separately; they do not belong in user-facing value lists. Update troubleshooting so exit 13 covers all doctor health failures, not only credentials/configuration.

Audit version examples only where they claim the current release; keep historical release notes and architecture decisions historical.

### 7.4 Make Cargo packaging hermetic

Anchor Cargo include patterns at the repository root. Prefer canonical absolute repository/docs-site links in the README so both the Cargo package and minimal binary release archives remain valid; otherwise include and validate every relative target in both artifact types. Ignored nested `README.md` and `LICENSE` files must not change the package file list.

Add a clean-export package test that checks an expected allowlist, validates README links in both the Cargo package and binary archive, and runs `cargo package --locked`. `cargo publish --dry-run --locked` may be a manual, non-gating check once crates.io ownership is ready; crates.io remains secondary and cannot block the GitHub release.

### 7.5 Make release publication depend on the full quality gate

Extract the common quality jobs into a reusable GitHub Actions workflow invoked by both ordinary CI and tag release. The release archive build and publish jobs must depend on:

- stable Rust formatting, Clippy, tests, install smoke, and package checks on Linux and macOS;
- focused behavioral tests on every native release runner, including Linux ARM64 and Intel macOS rather than build/version smoke alone;
- MSRV checks;
- telemetry worker tests;
- deterministic demo regeneration;
- proxy-environment Rust tests;
- documentation/install/package contract tests; and
- action/workflow linting.

Keep native archive builds for Linux x86-64/ARM64 and macOS Intel/Apple silicon, exact tag/version smoke checks, checksums, and provenance attestations. Add a non-publishing workflow-dispatch path that exercises the complete dependency graph. The real publish job remains tag-only.

Acceptance criteria:

- There is no workflow path to `publish` when any quality job fails.
- In non-publishing dispatch, a deliberately failed worker, demo, MSRV, platform-behavior, or documentation gate prevents a downstream release-rehearsal sentinel; no test branch can invoke the real publish job.
- v0.2.1 assets are never replaced or mutated.

## 10. Definition of done

v0.2.2 is ready only when:

- every finding in the disposition table is closed, and every behavior defect has a regression test that failed before its fix;
- request-capture tests prove local-input and rejected history operations send no content;
- concurrency tests prove telemetry opt-out is quiescent and notice-gated;
- program harness tests return within the documented deadline under descendant and pipe abuse;
- recovery resumes from every injected durable boundary and never downgrades forced provenance;
- recovery dry-run is byte-for-byte read-only and successful capture respects the global cap;
- history clearing preserves recovery evidence, redacted export is allowlisted, and every execution attempt is visible;

## Non-goals

- Sandboxing generated Python or preventing it from reading files available to the user.
- Universal rollback for shell, remote, package, database, or unmanaged effects.
- Native Windows support or a PowerShell parent-shell wrapper.
- A broad shell environment allowlist that would silently break credential-dependent commands.
- A new telemetry schema containing content, identifiers, exact paths, or timestamps.
- The Plan 9 provider benchmark or a model-selection change.
- Replacing or modifying the immutable v0.2.1 release.
